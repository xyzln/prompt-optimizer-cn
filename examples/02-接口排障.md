# 示例 2：接口超时排障（运维/后端场景）

## 原文（~110 tok）

> 我们那个登录接口最近老是超时，用户都投诉了，你帮我看看咋回事，是不是数据库的问题啊，前段时间还好好的，就这周开始的，你快点帮我解决一下，生产环境啊，别乱动

## 拆解

| 要素 | 内容 |
|---|---|
| 目标 | 定位登录接口超时根因并给修复方案 |
| 输入 | 代码仓库、监控面板（? 确认监控入口） |
| 硬约束 | 生产环境只读，不直接改 |
| 交付物 | 根因报告 + 修复方案（先报告后动手） |
| 成功标准 | P99 恢复到 <500ms（? 确认原水位） |
| 隐含前提 | 本周有变更（「就这周开始」）；用户猜数据库但只是猜测 |

## 框架

形态：先对齐再动手（生产环境 = 高风险）｜表达：现象 + 时间线 + 环境 + 交付顺序

## 压缩稿（~70 tok，省 ~36%）

```
排查登录接口超时：本周新发；P99 2s+（原 <500ms）；用户投诉。
环境：prod 只读；代码 api/auth.go；监控 Grafana login 面板。
步骤：对比本周变更 → 慢查询/连接池日志 → 定位根因。
交付：先根因报告 + 修复方案，批准后动手。
```

## 要点

- 「是不是数据库的问题啊」→ 只传症状不传猜测（猜测会锚定模型排查方向）
- 「就这周开始的」→ 保留时间线「本周新发」，并转化为排查动作「对比本周变更」
- 「别乱动」→ 量化为「prod 只读 + 先报告后动手」
- 「快点」→ 删（无信息）；加可验证目标「P99 <500ms」
