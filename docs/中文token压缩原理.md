# 中文 token 压缩原理

本文档沉淀 Prompt Optimizer-CN 的方法论依据。**诚实分级**：每条数据标注【实测】【官方】【社区共识】【传言】，不夸大。

## 1. 中文 token 汇率（各家分词器）

| 模型/分词器 | 1 汉字 ≈ token | 依据 |
|---|---|---|
| GPT-4 Turbo（cl100k） | ~1.5 | 【官方】OpenAI GPT-4o 发布页分词对比：同一中文例句 34 → 24 tok |
| GPT-4o（o200k） | ~1.0 | 【官方】同上，中文改善约 1.4× |
| DeepSeek | ~0.6 | 【官方】DeepSeek FAQ |
| Qwen / 通义千问 | ~1.0 | 【官方】千帆文档口径 1 tok ≈ 1 汉字 |
| 腾讯混元 | ~0.55（1 tok ≈ 1.8 汉字） | 【官方】混元文档 |
| Claude | 1~1.5 | 【传言】无官方中文实测，社区估算，**使用本工具输出 token 账时注意此为估算值** |

## 3. 文言文：为什么只推荐用于输出端

**结论：prompt 输入不文言化，输出约束可以文言化。**

输入端不推荐的原因：

1. **BPE 不按字省**：分词器按词元合并，文言单字词多、现代分词器对古文合并率低，实测省 token 有限
2. **古文语料占比低**：模型对文言 prompt 的理解可靠性低于现代中文，细粒度约束（数字、否定、边界条件）易丢
3. **歧义高**：文言省略主语/虚词，模型容易脑补出第二种解释
4. **阅读门槛**：prompt 是给人维护的工程制品，文言提高协作成本

输出端推荐的场景：要求模型「用文言/电报体**输出**」，在代码评审、批量摘要等大量输出场景省输出 token（单方自报 30~50%，见上表）。

## 4. 通用压缩原则（高引用方法论）

来自 linshenkx/prompt-optimizer、dair-ai 指南、brexhq/prompt-engineering、OpenAI/Anthropic 官方文档：

- **具体化第一优先**：模糊词 → 量化参数、范围、验收标准（各来源共识）
- **指令与数据分离**：数据用 ``` / XML 包裹，不与指令混排
- **正向指令替代「不要 X」**：模型对否定遵循差，正向表述既准又省
- **关键约束放末尾**：防长 prompt 中途遗忘
- **CoT「逐步思考」只在复杂推理加**：输出 token 也是成本
- **LLMLingua 思想**（Microsoft, EMNLP 2023）：删低信息量 token（冗余修饰、礼貌语、元话语），论文报告最高 20× 压缩性能近似无损
- **迭代优化 = 最小精准修改**：保留原意图与格式，新需求作为约束融入，不重写全文；`{{变量}}` 逐字保留

## 5. 负面案例（省 token 反而费 token）

【社区共识】以下做法得不偿失：

- 压丢否定词「不」、数字、单位 → 输出方向性错误
- 电报体歧义 → 模型脑补，答非所问
- 删结构标记（标题/列表/分隔符）→ 模型解析错误
- 压到模型需要反问澄清 → 多轮对话的总 token 远超省下的部分

**压缩不是目的，压缩后一次通过率才是。**
